## Findings

### F1 — Generic signup error masks the real failure (HIGH)

**File:** `web/src/app/auth/actions.ts:106-108` →
`web/src/lib/server/safe-error.ts:11`

When Supabase rejects the email (e.g., domain not deliverable), the
client sees `"Could not complete sign up."` with no detail. The actual
Supabase auth error is logged via `logServerError` server-side but the
user can't tell whether the problem is their email, their password,
their network, or our infra.

Concrete failure: signed up with `qatest1@orantene.com` (the user's
own custom domain). Supabase returned an error (likely sendmail
delivery rejection) but the UI surfaced nothing actionable.

**Fix sketch:** map known Supabase auth error codes to user-facing
messages — `email_address_invalid`, `email_address_not_authorized`,
`weak_password`, `over_email_send_rate_limit`, etc. Pass through the
specific reason for at least the email-side errors.

### F2 — Email-confirm enabled blocks the marketing → free flow (HIGH)

**Symptom:** signup completes server-side (auth.users row created) but
returns the message "Account created. Check your email for the
confirmation link, then continue signing in." For internal QA we have
to manually `UPDATE auth.users SET email_confirmed_at = now()`.

For real users in prod this is fine — Supabase sends the link. But on
localhost dev with email send disabled, every test signup is stuck.
**The Phase 8.x audit doc claims the flow worked with
`orantene+freeflow760905@gmail.com`** — that user must have been
manually confirmed too.

**Fix options:**
- (A) Disable email-confirm in the Supabase dev project so localhost QA
  works without manual SQL.
- (B) Add an admin "Confirm email" action in `/platform/admin/users`
  for super_admin to flip the flag from inside the app.
- (C) Accept the friction — document the SQL one-liner in a QA runbook.

Option B is the cleanest because it also helps support for prod users
who never received the confirmation email.

### F3 — Display name pulls from email local-part, not the lead's name (MEDIUM)

**File:** `web/src/app/onboarding/workspace/...` — workspace claim flow.

After provisioning `qatest-roster-2`, the admin shell greets the user as
**"Good evening, Orantene+Qatest2"** — the email local-part with `+` not
stripped. The lead row has `name = "QA Test Two"` which should be the
canonical greeting + display-name source.

**Fix:** in the workspace-claim action, copy `lead.name` into the
profile's `display_name` (and split into first/last if needed). Falling
back to email local-part is fine when the lead had no name — but here
we have one and we're ignoring it.

### F4 — "Add talent" canonical route is missing → 404 (HIGH; blocks E2E)

**Click target:** `RosterClientShell.tsx:1249` →
`href={`/${tenantSlug}/admin/roster/new`}`.

The route doesn't exist. Tried adding a redirect to the legacy
`/admin/talent/new` path (the only working talent-create form) but the
legacy admin layout gates on tenant membership through the
`(dashboard)` route group, which doesn't recognize the canonical
workspace tenant scope.

**Concrete impact:** a fresh Free workspace owner cannot add talent
from inside the canonical admin shell. They hit 404. The E2E test
"build 3 talent profiles on Free" is blocked here.

**Fix options (recommended A):**
- (A) Port the legacy `(dashboard)/admin/talent/new` form into
  `(workspace)/[tenantSlug]/admin/roster/new`. This is the
  F4-deletion-lane work the founder wanted to defer until launch — but
  this one surface is on the critical path now.
- (B) Build a minimal "name + display fields only" form at the
  canonical path that just inserts `talent_profiles + agency_talent_roster`
  rows and links to the rich editor on a secondary page. Faster to
  ship, less complete. About 1-2 hours.
- (C) Quick hack: rewrite the legacy form to ALSO accept the canonical
  `[tenantSlug]` so the canonical CTA can redirect to it. Brittle.

### F5 — Account & billing has no upgrade CTA when STRIPE_* env vars missing (HIGH; blocks E2E)

**File:** `web/src/app/(workspace)/[tenantSlug]/admin/account/page.tsx`.

When `isStripeConfigured()` returns false, the page shows
`"Billing not yet active. Contact support to upgrade."` — no upgrade
button. This means **the user cannot test the Free → Studio → Agency
upgrade chain on localhost without Stripe TEST keys**.

This is the right defensive behavior in production if keys aren't
provisioned, but on localhost the missing keys silently kill the
whole upgrade test surface. Also: the message says "Contact support"
which is wrong copy for a self-serve product.

**Fix options:**
- (A) **Prerequisite**: set `STRIPE_SECRET_KEY=sk_test_...`,
  `STRIPE_WEBHOOK_SECRET=whsec_...`, and the 8 `STRIPE_PRICE_*` IDs
  (test mode, all in Stripe Dashboard test environment) into
  `web/.env.local`. After that, the upgrade buttons render and we can
  run `stripe listen --forward-to http://localhost:3000/api/stripe/webhook`
  to see webhooks fire.
- (B) Soften the copy — "Billing keys not configured for this
  environment. Set STRIPE_SECRET_KEY and friends in .env.local, or
  upgrade in production." (only for dev, not prod).

### F6 — "Plan & integrations" Settings tab has no plan controls (MEDIUM)

The Settings page has a tab named "Plan & integrations" but clicking
it shows nothing actionable. The Free → Studio CTAs live on
`/admin/account`, not `/admin/settings`. Either the tab should link
through to `/admin/account`, or the upgrade buttons should mirror to
both places.

### F7 — 404 page is branded "IMPRONTA" instead of the active tenant (LOW)

When hitting any 404 inside `/qatest-roster-2/admin/*`, the not-found
page shows the **IMPRONTA** brand small-caps header. It should either
show the active tenant's brand (here: "QA TEST TWO") or be unbranded
("Tulala" platform fallback).

### F8 — Top-bar identity has unexplained "0" prefix (LOW / NIT)

The admin top-bar shows `0  orantene+qatest2  /  QA Test Two  Free` —
the leading "0" is presumably an avatar fallback that's rendering the
literal character instead of an initial or icon.

### F9 — "DNS: Tulala-managed" label format is unusual (NIT)

On Website's Domain & SSL card the rows read `DNS: Tulala-managed`,
`SSL: Active · auto-renew`, `Records: Path-based`. The "DNS" row reads
oddly because the value isn't a state — it's a provider. Try
`Provider: Tulala` or `DNS host: Tulala` instead.

### F10 — Continue with Google + Create account buttons are gold/yellow (NIT)

The auth pages render the primary buttons in a gold/amber against the
dark theme. Contrasts oddly with the Tulala dark scheme. Could be
deliberate for accessibility but worth a styling pass.

## Blockers for completing the E2E test

To run the full Free → Studio → Agency chain the user needs to:

1. **Provide Stripe TEST keys** — set in `web/.env.local`:
   ```
   STRIPE_SECRET_KEY=sk_test_...
   STRIPE_WEBHOOK_SECRET=whsec_...   # from `stripe listen` output
   STRIPE_PRICE_STUDIO_MONTHLY=price_...
   STRIPE_PRICE_STUDIO_ANNUAL=price_...
   STRIPE_PRICE_AGENCY_MONTHLY=price_...
   STRIPE_PRICE_AGENCY_ANNUAL=price_...
   STRIPE_PRICE_TALENT_PRO_MONTHLY=price_...
   STRIPE_PRICE_TALENT_PRO_ANNUAL=price_...
   STRIPE_PRICE_TALENT_PORTFOLIO_MONTHLY=price_...
   STRIPE_PRICE_TALENT_PORTFOLIO_ANNUAL=price_...
   ```
   Plus run `stripe listen --forward-to http://localhost:3000/api/stripe/webhook`
   in a separate terminal so webhook events reach the local server.

2. **Decide on F4 fix** (port talent-create form, build minimal one,
   or hack legacy). I'd recommend a minimal form (Option B above) —
   maybe 90 min of work — so the canonical admin shell is self-sufficient.

3. **Fix the F1/F2/F3 polish** in parallel — they're independent and
   each takes ~30 min.

Once unblocked, the E2E test resumes:

- Mint a 100%-off promo code via `/platform/admin/billing/discount-codes`
  (already shipped — the surface needs Stripe keys to actually mint).
- Build 3 talents.
- Click Upgrade to Studio in `/admin/account` → Stripe Checkout opens
  with the Studio price → enter promo code → 100% off → success.
- Webhook fires → `agencies.plan_tier` = `studio` → admin shell shows
  Studio badge + builds 4 more talents.
- Upgrade to Agency. Same flow.
- Cancel via Billing Portal (or downgrade) → `plan_tier` = `free`.

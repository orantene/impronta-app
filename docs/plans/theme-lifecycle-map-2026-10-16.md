# Theme lifecycle map (TUL-418 / L1), read from code on origin/main, 2026-10-16

Docs only. Nothing here was run; every statement comes from the header comment or exports of the named file. Docs-only PR for TUL-418 (L1).

## The chain, stage by stage

| # | Stage | What happens | Code (all under web/src) | Guard / safety |
|---|---|---|---|---|
| 1 | Edit | An admin edits a design in Builder Lab; the result is a design payload plus a draft | components/builder-lab/*, platform/admin/builder-lab/talent-designs/publish-actions.ts | Publish confirms in the in-app dialog and lists blocking issues (#3899) |
| 2 | Diff | Two payload versions become candidate release items: token-default, variant-default, copy, new-block, layout, code (critical is never generated; the admin flags it) | lib/talent-site/theme-releases/diff-payload.ts | Pure. Copy-only drafts produce `copy` items, so they are publishable |
| 3 | Classify | Each keyed node in a site tree is untouched, edited or removed against its design stamp; unstamped or duplicate-key nodes are talent-added | theme-releases/classify.ts (+ origin.ts) | Pure; stamps are hashes of design-owned props |
| 4 | Release channel | Channel change as one function with injected effects: demos, optin (needs rollout > 0), default (flips catalog row first) | theme-releases/manager/channel.ts, dry-run.ts | `checkChannelChange` runs before any effect; a refused change touches nothing; authored-sync gate |
| 5 | Demos | Demo profiles (`is_demo`) update automatically on every release: three-way merge when the base is exact, else full re-apply keeping content; live demos then publish | theme-releases/manager/demos.ts | Talents and QA users are never passed in (`talentSitesOnly`) |
| 6 | Fan-out | "Open to talents" creates update rows and bell entries once; lazy fan-out later covers sites that land below an open release | manager/fan-out.ts, lazy-fan-out.server.ts | Idempotent, best-effort, respects rollout bucket and skips demos |
| 7 | Talent update | The talent sees the update notice and sheet, merges onto their customized draft | components/talent/site/theme-update/*, theme-releases/talent-update/*, merge.ts | Merge keeps edited parts, updates untouched ones; L2 matrix test names every case |
| 8 | Apply to draft | Design apply and upgrade write the DRAFT (same writer and history entry) | server/theme-apply-core.ts, design-upgrade.server.ts, history/writer.ts | Publish only when live already equals draft, so an upgrade never ships unpublished edits |
| 9 | Publish | Draft goes live through the publish path | server/demo-pipeline.server.ts (service role) | Per-site checks before publish |
| 10 | History and undo | Snapshots, restore (draft write only), undo of one theme update with reverse merge | history/history.server.ts, restore-plan.ts | Restore never deletes history and never touches the live site |

## What is proven by tests on main (no DB)

- Restore/undo planning: `history/restore-plan.test.ts`, `timeline.test.ts`, `writer.test.ts`.
- Channel guards and demo targeting: `manager/*` tests, `demo-channel-loader.test.ts`.

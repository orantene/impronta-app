## 2. The three blocks and their registrations — CEO ruling 2026-09-05: the SELF-FETCH class

`ticket_picker` (and `event_list`, `event_hero`) are **self-fetch islands, exactly like `reserve_table` and `session_picker`** (CEO, by precedent): no entry in `native-data-block-needs.ts`; tenant and event come from props; registered through the same twelve-file landing Dashboards mapped for `session_picker` (`create.ts`, `registry.ts`, `render.tsx`, `drop-policy.ts`, `mvp-allow-list.ts` ×3, the island, the inspector, the icon, the i18n keys, the static allow-list test). This supersedes §6a's "declare needs" choice for these blocks. Two pickers on one festival page are safe in this class because **each island fetches by its own `eventId` prop**, not from a shared page-level source.

**The one guard that makes the class safe, written here because the precedent does not have it:** `render.tsx:5551` passes `SessionPickerIsland` `tenantId={options.dataSources.tenantId ?? ""}`. Sessions proved the mechanism (2026-09-06): `""` is refused by the action's zod schema (`z.string().uuid()`) **before any query is built**, so it is not a data exposure — the tenant-scoped read is the second line, not the first. What is wrong is the *message*: the refusal renders as `unavailable` / `invalid_request`, the same answers an outage gives, so an author who dropped the block on a page with no tenant looks for the fault in the engine. **Two rules for the ticket picker, both required:** (a) the server actions' schemas take `tenantId: z.string().uuid()` and `eventId: z.string().uuid()`, so an empty id cannot reach a read at all and the tenant predicate is defence in depth; (b) the island renders an explicit **`not_configured`** state when `tenantId` or `eventId` is empty, structurally distinct from `unavailable` — never a blank picker, never a fetch with a default. Sessions is adding the same guard to `session_picker` as its own PR; E5 copies that shape rather than re-deriving it. Preview substitution (`previewSubject?.id` for the tenant) is to be verified on the render path before the block ships, against a real event, not a fixture.

## 3. Decisions taken in this doc (say so if any is wrong)

1. **`perUnitDomainRow: true` on every ticket capacity need.** Contract from `capacity-requests.ts`; written into the plan on 2026-09-05. Without it refund-by-line cannot free one seat.
2. **Line = (offering, variant, session, units).** The mint reads `variant_id` for `admits_per_unit` and `session_id` for the anchor; both are already columns on `order_lines`.
3. **No remaining counts on the picker.** Sale state and price only; "sold out" is the reserve's answer, surfaced from `createPurchase`'s `sold_out`.
4. **Pay-at-the-door — RULED as B′ (Director, 2026-09-06, third and final ruling, after verifying the cap themselves: `CHECK (hold_ttl_seconds BETWEEN 30 AND 604800)` is a column constraint in `…200` as well as the function check, so "TTL = door time" was unimplementable beyond a week).**
   - **Hold at creation, TTL = the session's END — not its start.** Freed after the night, never while a guest is in the queue. START reintroduces the exact race B′ removes: a hold expiring at 21:00 for a 21:00 show frees the seat while the guest is in the queue or walking in late, and the door then disagrees with the system on a night that is genuinely sold out. The gap between start and end is a few hours on one night, during which the seat is unsellable anyway; END removes the race entirely rather than narrowing it. There is no case where START is safer than END, and one where it is worse.
   - **Pay-at-the-door is offered only when the session ends within the 7-day cap.** Card only beyond it. The cap stays where it is: raising it would make the hold state do the commit state's job — a venue promising a seat to someone who will pay cash three months out is extending credit, not holding a seat.
     **Why seven, in the migration's own words** (`…200`, at the column): *"tickets want ten minutes, tables fifteen, a quoted job still wants two days. 30s floor, 7d ceiling."* Seven days is 3.5× the longest use its author could name — headroom over two days, not a load-bearing invariant and not evidence that ninety days is safe. A door hold for an event three months out would stretch the ceiling ~45× past its stated design range; a number picked as headroom over two days is evidence that nobody intended a hold to live that long. So the CEO's option (a), raise the cap, is declined on the migration's own sentence, and (b) stands: door orders are refused visibly beyond the cap with card offered — which satisfies the one thing the CEO will not accept, a door hold that silently expires before the door, by never creating one that can. Falsifiers on the QA row: the option silently absent, **and the option offered beyond the cap** (offered-then-`CP007` is the same silent failure one step later).
   - **Commit at settlement**, when `markPaid` runs and a person is standing there.
   - **No-show = the ordinary sweep at session end.** Bounded, automatic, visible on the night report.
   - **The rule must be said, not silently applied (the addition):** when pay-at-the-door is withheld by the cap, the picker tells the guest, in their words — *"Paying at the door opens closer to the date"* — and the operator surface where `allow_pay_in_person` lives says the same, so the rule is discoverable before it is experienced. A venue owner who enabled the toggle and cannot see it on their own event page will file the setting as broken. The state is fine; the silence would be the defect.
   **Two edges (Capacity, 2026-09-06), decided here:**
   - **Reschedule invalidates holds silently.** `expires_at` is a fixed instant (`now() + ttl`), not a reference to the session; move the night two weeks later and every hold still expires at the OLD session end, the reaper frees the seats, they are resold, and the ticket-holder arrives to someone else in their chair — on exactly the night the venue is already apologising for. No primitive can change a TTL today (re-holding releases first, and someone else can take the seat in between). **Capacity builds `extend_capacity_hold(p_allocation_ids uuid[], p_ttl_seconds int)`** at E5 time, to this contract (Capacity's own correction, because a reschedule's allocations are mixed-state — some held, some already paid and committed): `hold` → extended (`expires_at = now() + ttl` under the pool's row lock, same 30…604800 bounds); **`committed` → skipped, not an error** (no TTL, already immune; failing on it would punish the caller for passing the complete set, which is the safe set to pass); **`released` → RAISES** (extending it would resurrect a seat that may have been resold — the only dangerous input); **returns `{extended, skipped_committed}`**, never void, so a caller that expected forty and extended two finds out. **Sessions' reschedule applier is the caller** — and it does not exist yet: nothing in `web/src` updates `sessions.ends_at` (the only `ends_at` reschedule is on `agency_bookings`), and `planSeriesEdit` has zero non-test callers; #1780 shipped the create path only. So there is no live exposure and no retrofit: the rule is a **precondition of the applier** — it does not ship unless moving `ends_at` extends every live hold on the session's `session_tier` pools **in the same transaction as the move** (a reaper pass between the two frees the very holds the move was meant to protect), and a move beyond the 7-day cap surfaces the event (the guest is told and offered card) rather than leaving holds silently short. The generalisation, in Sessions' words, which this repo keeps paying for: *a value derived from a mutable field, stored, and never re-derived — an absolute `expires_at` from a session end, a duration added to a wall clock, a refusal computed once and persisted — looks correct at write time and is wrong only after something else moves. A derived value must be recomputed on read or repaired when its input moves; storing it and doing neither is the bug.* `extend_capacity_hold` is the repair, so the applier owes the call.
   - **A purchase after the session has started gives a negative TTL (`CP007`).** Decided as a product rule, not a clamp: **online pay-at-the-door closes when the session starts.** A person buying during the show is standing at the venue, and that sale is the door's `sellAtDoor` (already live), which commits immediately and holds nothing. The picker offers card only once the session has started, with the sentence "Doors are open: pay at the door in person." A 30-second clamp would sell a seat online to someone who is not there.
   History kept as the reasoning: commit-at-creation (ghost room, unbounded) → hold with TTL = door time (refused by `CP007` beyond 7 days; races the guest at the door) → Capacity's commit-on-confirm (in the guest case the click is the confirmation, so the ghosts return under another word) → B′. Build items: per-leg `ttl_seconds` on the batch and `extend_capacity_hold` (Capacity); the `createPurchase` shortest-TTL collapse and a door-hold exemption (Orders); the reschedule hook calling `extend_capacity_hold` (Sessions); none blocks step 1.
5. **No QR before payment.** A QR is an admission; an admission is minted on `paid`. An in-person receipt shows the amount and the code, and becomes a ticket at the door.
6. **Promo applies at `createPurchase`** through `PurchaseInput.promoCode`, so the discount is the order's, never re-derived on the receipt (the `?promo=` orphan lesson).
7. **Free events** (`reserve_mode = 'free'`, amount 0): same path, `paymentChoice: "full"`, `collect: "none"` → paid immediately → mint. No Stripe hop.
8. **Deposit** tickets are **out of scope** for E5 (a deposit on a ticket is a layaway; not asked for).
9. **Disposable email domains are NOT refused at ticket checkout — OVERTURNED by the Director on a fact the doc had wrong.** The premise "a ticket sent to a burner is unrecoverable" is false: the door already lists admissions and **finds a guest by name** (`door-client.tsx` "Find by name"), so a buyer who cannot open their email walks up, gives their name and is admitted — a recovery path that works with a dead phone; and a refund goes to the card, not the mailbox. A refused sale is the unrecoverable direction: a blocked buyer closes the tab. Alias and forwarding providers are real people, and this repo has already paid for that guard once (five hard bounces). **Instead, one true sentence at the email field:** *"Your ticket goes here — and if you cannot open it, we will find you by name at the door."* Per-tenant strictness is a later setting on evidence; never a silent block.
10. **A buyer refunded because the seat went during payment is TOLD, in the same breath as the refund** (Director's addition to §5b.0). A silent refund reads as fraud or as the venue cancelling, and the buyer — the one person who does not know they have no seat — may travel to the venue. The refund carries the message: the seat went while payment was completing, they are refunded in full, and what to do next (buy again if seats remain, or contact the venue). QA row: the falsifier is a refund with no message.

## 5a. A consequence to choose, not discover: pay-at-the-door and capacity

Under **commit at creation** (first draft): a hundred committed pay-in-person seats and a bad night is a room sold out and empty with no money taken, and **nothing reclaims the seats** — the exposure is unbounded and invisible from the toggle. Under **hold at creation with a door-order TTL** (Orders' recommendation): the same seats return to the pool when the TTL lapses, so the exposure is bounded by the TTL and a guest who arrives after it is the case the TTL length must be chosen for. Either way, whoever enables `allow_pay_in_person` for a real venue is choosing an exposure, and `no_show_at` is where the evidence for any cap or cutoff will come from. This design does not cap it.

## 5b. Blockers found in review (Orders, 2026-09-05) — not details

0. **Payment can land after the hold lapsed, and no `expires_at` value removes that — the webhook-time re-check is the requirement (Finance).** What exists on main: `completeOrderForTransaction` already re-checks at webhook time — `commit_capacity` REFUSES an expired hold rather than reviving it, and the order still flips to `paid` (its DECISION 2: a completed charge is never rolled back to tidy a ledger; it logs `CAPACITY_LOST_AFTER_PAYMENT` for a human). **The gap for tickets:** `onOrderPaid` then fires and the mint would issue admissions with no committed allocation — a ticket that does not exist, which is the exact case Finance names. **Rule for E5, in two places, because of where the hook sits (Orders' objection, accepted):** (a) **In the hook**, `mintAdmissionsForPaidOrder` mints a ticket line ONLY when its committed allocations exist; a line whose hold was lost mints nothing and **records the intent** — a `ticket_refund_intents` row (`order_line_id`, reason `seat_lost_after_payment`, `created_at`, **`claimed_at`**, `executed_at`, `result`; migration from `…800`) — and nothing else. It must NOT call the refund executor from inside `onOrderPaid`: that hook swallows every subscriber error by design (`complete-order.ts:225`, correct for minting), which would turn `refundOrderLines`' one outcome that needs a person — `partial_failure` with `movedCents > 0`, money moved then a leg failed, not retryable — into a log line and an `ok`; and a refund issued microseconds after the charge can be refused by Stripe before settlement (`refund_refused`, `movedCents: 0`), which the hook would also swallow, leaving the customer charged for a seat that does not exist with nothing anywhere saying so. (b) **A separate executor path** (a small cron over unexecuted intents) **claims before it executes** — `UPDATE … SET claimed_at = now() WHERE id = $1 AND claimed_at IS NULL`, and a zero-row result means another run has it and the loser skips (Orders; the same atomic check-and-write that makes `redeem_tenant_promo` correct). `executed_at` is written after the refund, so a crash between "Stripe refunded" and "row updated", or two overlapping runs, would otherwise refund twice; `planRefund` refusing `line_already_refunded` is real protection but downstream, and a future partial intent (2 of 4 tickets) would slip past it. A claimed-but-unexecuted intent is visible as exactly that — something to investigate, never something to redo. Then it calls `refundOrderLines` where its result is inspectable and retryable: `refund_refused` retries after settlement; `partial_failure` pages a person; success writes `executed_at` and **sends the buyer's message with the refund** (decision 10). Automatic, no human in the loop on the happy path, and the first automatic caller of Orders' executor — **the one caller where nobody is watching the result**, which is why placement matters more than policy. Re-entrancy is safe under either shape (`completeOrderForTransaction` returns early on an already-`paid` order; `planRefund` refuses an already-refunded line). The receipt shows the line as refunded with the reason. Finance's note stands beside it: until `refund.failed` is subscribed on the live endpoint, a failed refund is silent — Finance's item.
1. **Which Stripe webhook route is live? — CLEARED by construction** (Director, verified by reading the routes). `/api/stripe/webhook` and `/api/webhooks/stripe` are **two thin shims over one `handleStripeWebhook`**; each header says so: *"Both routes now delegate to the same handleStripeWebhook, so EITHER configured endpoint behaves identically and shares one idempotency ledger"* — the historical failure (two implementations, whichever URL Stripe was NOT pointed at silently dropped its money flows) is the one already fixed. The handler is the union of events (`checkout.session.completed`, `payment_intent.succeeded`) with one idempotency claim and imports `markPaid`, so the guest path settles on whichever endpoint Stripe points at. Corrections: there are **four** Stripe-ish routes, not three — `api/webhooks/stripe-v2` is genuinely separate (its own `STRIPE_V2_WEBHOOK_SECRET`, reconciles the payouts ledger, not on the guest path) and `api/discover/subscriptions/webhook` handles subscriptions. For operations: the live platform endpoint is `https://app.tulala.digital/api/webhooks/stripe` (`we_1U1rrP5C0mUEeRd1FXf7WWRL`, Finance). It does not gate this build.
2. **Checkout expiry is unset today — but the gap is NOT live** (Orders, corrected on re-check): the only Checkout caller, `client-pipeline.ts`, never touches capacity, so no current path combines a hold with a Checkout. It becomes real the moment E5 points the picker at Checkout. Sizing: `orders.hold_expires_at` is already written by `createPurchase` (`purchase.ts:596`) as the shortest TTL across the cart's pools, so the fix is **an existing value passed to a parameter that does not yet exist**, clamped to Stripe's 30-minute floor with the hold staying the tighter constraint — **and the clamp is not the fix**: at the default 900 s hold the session outlives the hold by the amount it was clamped, so item 0 above is what closes the window. Orders is deliberately not pre-building it (a parameter for a caller that does not exist is the flag-nobody-passes shape); it lands with E5. Genuinely small. **Blocker 1 is the one that can cost a customer money.**

Verified by Orders, so the build can rely on it: `createCheckoutSessionForTransaction` is guest-ready (`customer_email`, no Stripe Customer); success/cancel URLs are caller-supplied; `markPaid` already fires `onOrderPaid` → mint; the Checkout idempotency key is `cs_txn_<transactionId>`. Guest identity on Stripe (Finance): payment mode with `customer_email` and `customer_creation: "if_required"` creates no Customer object — guest customers in the Dashboard — so **nothing is built on Stripe identity for these buyers**. Registrations Finance asked about, verified: `/r` is in the surface allow-list (`gate.ts:40` via `CANONICAL_RECEIPT_PREFIX`, `path-groups.ts:354`) and reserved five ways; El Paisa's host `elpaisa.tulala.digital` is in `agency_domains` (active), so middleware serves the receipt after the charge. And one behaviour to state so it is not mistaken for a bug: `ensureCustomer` treats **email as identity** — two guests typing the same address become one customer with a merged history.

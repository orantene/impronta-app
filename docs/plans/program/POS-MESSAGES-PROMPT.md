## Architecture (decided; do not redesign)

- **One store.** The POS inbox, the workspace Messages page, and the customer thread all read `inquiries` + `inquiry_messages`. You add columns and tables; you do not add a second conversation model.
- **New columns on `inquiries`** (additive, nullable, backfilled by a migration): `conversation_state` (`needs_reply|awaiting_customer|resolved`, derived on write by a trigger from the last message's sender and explicit resolve/reopen), `opportunity_state` (nullable, derived from `status`/`current_offer_id`/deposits), `owner_user_id` already exists (MS06 owner = who replies; it is a permission, not a professional), `last_customer_message_at`, `last_staff_message_at`, `resolved_at`, `resolved_by_user_id`, `lost_reason`, `channel` (`web_chat|whatsapp|sms|email|counter`), `location_slug` (default `default`).
- **Records linked to a conversation**: table `conversation_records (id, tenant_id, inquiry_id, record_kind 'order'|'appointment'|'reservation'|'class_enrolment'|'tickets'|'project'|'offer', record_id, linked_by, linked_at, unlinked_at, version)` (MS11: several records on one conversation; MS05B: re-linking shows impact first). Chips on the row and the panel read the record's own state through the existing readers.
- **Customer identity on a conversation** (MS04/MS05): `inquiries.client_contact_id`/`client_account_id`/`customers` are the link targets; a `conversation_identity (inquiry_id, level 'none'|'linked'|'confirmed'|'granted', method 'phone'|'email'|'sms_code'|'name_only'|'staff', confirmed_at)` row records the level: linking (internal, shows history to staff) ≠ confirming identity (a known detail or an SMS code) ≠ granting the customer access to their records. Matching = three levels (phone match, name-only similarity, new) computed by a pure `matchCustomers()` over `customers` for the tenant.
- **Cards** are `inquiry_messages` rows with `message_kind` in a new closed set and a typed `card_payload`: `menu_options`, `item_config`, `basket`, `service_card`, `professional_times`, `class_card`, `tickets_card`, `offer_review`, `offer_state`, `payment_request`, `order_confirmation`, `appointment_confirmation`, `change_request`, `change_result`, `reminder`, `internal_note` (never delivered), plus `text`. The card's own state (`sent · viewed · selected · paid · expired · unavailable · price_changed · cancelled`) lives in `card_payload.state` and is updated by the engine, never by the client. One pure module `lib/messaging/cards.ts` defines every payload type and its render model for both the operator thread and the customer thread; one static test proves every kind has an operator renderer, a customer renderer, and an SMS plain-text fallback (MC12).
- **Shared draft** (MS08): a draft `orders` row with `orders.inquiry_id` (add the column if absent) and `source_channel = 'messages'`; both the customer card (MC03) and the operator panel mutate it through `pos_mutate_draft_line` under version lock; the customer side goes through a guest-scoped server action that checks the conversation token. The pickup/appointment slot is held only while the payment link is valid (MC03 rule): the hold's `expires_at` = the link's `expires_at`.
- **Payment request** (MS14/MS15/MC10/MC15–MC20): `requestPayment(conversation, record, amountKind 'deposit'|'full'|'none')` → `pos_reserve_collection` + `payment_links` (package 1) + a `payment_request` card; `/pay/<code>` is redesigned to MC15–MC20 (review lines, total in currency, what is kept until when, method, processing with 3-D Secure, declined, unknown, return to thread with the receipt, closed/expired/paid-as-hold-ended/deposit-then-balance/free-booking/receipt-failed edge states). Paid → the engine writes the record (order paid → kitchen ticket via the existing prep path; appointment deposit paid → hold converts to booking via the existing writer), posts `order_confirmation` / `appointment_confirmation`, and the thread state becomes `awaiting_customer`; it never resolves.
- **Recovery model** (MS19/MS19B/MS20/P11/P12): four situations as data, one action each: `kitchen_delivery_failed` (retry the prep ticket by id / print at counter), `finalization_failed` (payment confirmed, order not written: recover from the saved checkout `checkout_snapshots (id, tenant_id, inquiry_id, payment_link_id, basket jsonb, customer jsonb, promised_at, provider_ref, created_at, recovered_order_id)` written BEFORE the link is minted; recovery writes the order from the snapshot, never charges), `payment_unknown` (check status via the reconcile path; never request again), `promised_time_unavailable` (offer next slot / authorized refund through the existing refund path). Basket-changed-after-checkout (MS20): the link is locked to a basket version; a later edit refuses `checkout_locked` until the link is cancelled. Concurrent edit (MS18): the panel carries `version`; a stale save shows the precise diff (previous / theirs / yours) built by a pure `diffDraft()`.
- **Channels**: `lib/messaging/channels/{web-chat,email,whatsapp,sms}.ts` behind one interface `{send(message) → {ok, providerRef} | {ok:false, reason:'channel_unavailable'|'template_required'|'rate_limited'}, deliveryStatus(providerRef)}`; email = Resend (cards render as summary + links); WhatsApp and SMS = adapters with the provider call behind env keys (`WHATSAPP_*`, `TWILIO_*`), returning `channel_unavailable` when unset (MS21: "web chat can only be opened by the customer"; WhatsApp needs a template first, 24 h rule); inbound webhooks under `api/webhooks/messaging/<channel>` verified by signature, appending `inquiry_messages`. Delivery states per message (MS23): `message_delivery (message_id, channel, state 'queued'|'sent'|'delivered'|'read'|'failed', provider_ref, attempts, last_error, updated_at)`; a failed send is kept and retried once through `outbox_messages`.
- **Reminders** (MS26): `scheduled_messages (id, tenant_id, inquiry_id, record_kind, record_id, send_at, body, card_kind, state 'scheduled'|'sent'|'cancelled'|'failed'|'auto_cancelled', created_by)`, one per record (unique partial index), auto-cancelled when the record is paid/cancelled; cron `api/cron/messaging-reminders`.
- **Follow-up queue** (MS16): a reader over `inquiries` grouped by owner with one action per row; "close as lost" writes `opportunity_state = lost` + `lost_reason` and never touches records.
- **Post-purchase change** (MS17/MC13): reuses `reschedule_booking_set` / `cancel_booking_set` with the exact policy check from package 2's `booking_policy_overrides` (the card states "requested Mon 14 Sep 09:12, 24 h 48 min before the appointment; free until 10:00 Tue").
- **Unread, badge, toast** (MS01/MM06): unread = `inquiry_message_reads`; a rail badge count per location; an incoming message during an open card attempt is a discreet toast, never a navigation.
- **Search** (MS25): `body_tsv` already exists; results show the matching snippet; opening lands on the message.
- **Concurrent operator edits** (MS18, P12): `version` on the draft and on the offer; refusal `conflict` with the three-way diff.

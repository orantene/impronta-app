## What failed, and what was fixed in the application

**Defect 1 — "Still owed" was a 200-row window presented as a total.** `PaymentsPage` summed `filterOrders(loadWorkspaceOrders(...), {bucket:"to_pay"})`, and `loadWorkspaceOrders` reads the 200 most recent orders because it feeds a list. Reproduced live twice on the git-built host before the fix: run 7 printed **$821.00** when the rows said **$1,209.00** (286 orders, 28 of 46 owed orders inside the window), run 9 printed **$713.00** against the same $1,209.00 (299 orders). `sql/03-owed-window-vs-set.sql` holds the query and both readings; `run7-…/` and `run9-…/` hold the screenshots and the page snapshot (traces kept uncommitted, see above). Fix: `loadTenantOwedOrders` in `_data-bridge/payments-activity.ts` pages through EVERY `pending_payment` order with a positive total and their PAID transactions; `sumOwedByCurrency` in `lib/payments/activity-shape.ts` applies the desk's own `salesBucket` + `outstandingCents` per currency; the page uses them; three unit tests in `activity-shape.test.ts`. Runs 12 and 13 read $1,209.00 on the fixed host.

**Defect 2 — every Order row on Sales linked to a page that does not exist.** `orderHref` built `/admin/orders/<id>`; there is no such route (the runtime log shows the browser's prefetches of every row 404ing), so a manager who clicked a sale landed on "This page is no longer here". The Payments refunds column had the same link. Both now point at the desk's search, `/admin/orders?q=<id>`, which the client record and the project page already used and which matches on the id prefix.

**Defect 3 — Create booking failed and printed the database's words.** On the accepted offer, `Create booking` returned `operator does not exist: uuid ~ unknown` and the work page rendered that sentence as its status. Cause: the branch database's `bookings_write_order` was the `20261228000143` body, matching `inquiry_offer_line_items.source_service_id` against a uuid regex, although `20261228000144` retyped the column to uuid and re-created the function without the regex, and `schema_migrations` listed both as applied (`sql/02`). Repaired with `supabase/migrations/20261231180621_reassert_bookings_write_order_uuid_body.sql`: the 000144 body verbatim, the grants, and a DO block that refuses a regex on the uuid column. Applied to the branch through pg with its `schema_migrations` row; live md5 `b98d2f5d…` → `f83fabf8…`. The raw-error rendering is NOT fixed here: `_pipeline-actions.ts`'s convert action falls through to `reason` for anything it does not recognise and is English-only throughout; it belongs to the work-detail owner (finding below).

**Carried over and finished — the refund desk spoke in codes.** `refund-desk-copy.ts` maps every engine refusal to a message key in en/es/fr; `refund-execute.ts` returns a `code` beside its English `error`; `refund-execute-lines.ts` forwards the provider's code; the form renders the sentence and stays open on a refusal. Not exercised in the browser (no refundable card payment exists on this fixture and cash cannot be refunded at Stripe); covered by `refund-desk-copy.test.ts` in `test:money`.

## What the spec does that a reader should know

- **Shared fixture.** Four sibling journeys write to this workspace at the same time. A drawer another session left open is waited on for three minutes and then closed through the Shifts screen (annotated, screenshot `05a` in run 7); Expected cash is the float plus the rows stamped with this shift, whatever else landed in it; "Still owed" is asserted over the whole owed set and the whole workspace under the same rule.
- **One-way door.** Create booking converts the inquiry; the fixture has one accepted offer. Section 5 converts when unconverted, cancels when a pending order exists, and otherwise reads the project as it stands and says so in its annotations. Run 12 watched both; run 13 read the resulting state. The inquiry `6a5e9455…` is now `booked` with one cancelled $800.00 order and two `booking_talent` rows; a sibling that expected it `approved` and unconverted will find it changed.
- **The wrong rule is computed on purpose** (`total − collected` over every row) so agreement with the query cannot be a tautology.

## Not proven, and why

- **A draft order against a project.** No interface path creates one: orders attached to an inquiry are minted `pending_payment` by `bookings_write_order`, and the counter's draft is a standalone sale. Proving it would mean inserting the very row, so it was not done. The counter's draft was proven not to enter the workspace's owed figure, and `owedCents`/`sumOwedByCurrency` exclude drafts by unit test.
- **Takings split from card.** No card taking exists and none can be made on this fixture (no reader, D-POS-4). The cash row stands alone; a workspace with a card row would get its own row by `paymentMethodKey` (unit-tested), not by this journey.
- **Production's copy of `bookings_write_order`.** Not read (host unresolvable from here). Unknown whether the drift exists there.
- **The refund desk in a browser.** See above.

## Environment findings that cost time (not application defects)

- **Vercel build container.** Every build of `deca2efc8` on the 4-core / 8 GB container hung past 45 minutes ("Creating an optimized production build" and nothing after), while CI compiled the same commit in 107 s on 16 GB and this machine compiled it in 2.4 min at 2.9 GB peak RSS. Later git builds (`ab1737155`, `dcefb0b2`) succeeded in 4-6 min, so the cliff is marginal. To get this branch onto the host at all, the output was built here (`vercel build` with the branch-scoped env pulled via `vercel pull --git-branch=program/journeys-2026-09`) and uploaded with `vercel deploy --prebuilt` from a throwaway clone checked out on `program/journeys-2026-09`, so the deployment carried `githubCommitRef: program/journeys-2026-09`, the isolated env attached, and the three QA hosts auto-assigned. Two traps in that path: Next traced every `web/.env*` file into every function (so `.env.local` and the isolated env file, both secrets, were moved out for each build; only the tracked `.env.example` remains in the trace), and the macOS-built bundle traced the darwin `sharp` binary, which made the first server action on each fresh deployment crash the Lambda (`Could not load the "sharp" module using the linux-arm64 runtime`, runtime log 17:49:36Z) until `@img/sharp-linux-arm64` was installed with `--no-save` for the build. Each sibling merge re-pointed the hosts to a git build without this branch's fixes (16:08Z, 17:09Z), which is why runs 7 and 9 caught defect 1 live.
- **Version skew.** A run that started right after an alias switch posted a server-action id the new build did not have and got a 500 with an empty alert on the counter. `next.config.ts` sets `experimental.skewProtection`, which Next 16 rejects as an unknown key, so nothing protects against this today.
- **The counter's basket once did not repaint** after a 10-second add-line action although the row was written (run 6, order 45944810…, line at 16:21:29.04Z, refresh 200 ms later); the sibling counter journey has seen the same. The spec now awaits the row first so the failure names the screen. Not reproduced on runs 7 to 13.

D-MSG-2 · 2026-09-17 · One thread-type rule. `inquiry_messages.thread_type` "private" is the CLIENT thread (staff + client/guest); "group" is the TALENT thread (staff + invited talent). Every staff-authored POS message, replies, cards and internal notes alike, is written to "private" (`threadTypeForStaffMessage` in `web/src/lib/messaging/thread-rule.ts`); the engine never writes "group". Internal notes are `message_kind = 'internal_note'` on "private" so staff see one conversation, and EVERY client-facing reader (workspace client page, `/api/client/messages`, guest dock + `/c/[inquiryId]`, `/c/t/[token]`, and the talent inbox reader) excludes that kind. Staff readers (POS `loadMessagingThread`, classic `loadInquiryMessages`) read everything and each POS ThreadMessage now carries `thread`. Evidence for the rule: before S1 the engine wrote replies to "group", which no client surface reads (a POS reply never reached the client), and wrote notes to "private", which `loadInquiryMessages` and the guest reader served unfiltered (a note reached the client). The DB trigger `messaging_touch_inquiry_from_message` already returns early on `internal_note`, so a note never flips conversation state. Enforced by `web/src/lib/messaging/client-readers.static.test.ts`.

D-MSG-5 · 2026-09-17 (S4) · `messagingMerge`'s "refuses if either has a paid or confirmed
record" guard is real only for `order` (`orders.status` paid/fulfilled/partially_refunded) and
`offer` (`inquiry_offers.status` accepted) — the two record kinds with an actual status column
reachable in one hop. `appointment` / `reservation` / `class_enrolment` / `tickets` / `project`
have no dedicated status table wired into Messages v5 yet; `RecordChip.paymentState` /
`fulfilmentState` are `null` everywhere in the existing engine too (see `inbox.ts loadChips`,
`essentials.ts` — pre-existing, not introduced by S4). Those five kinds are **not checked** by
the merge guard; a merge that should have been blocked on one of them will not be. Documented
in `web/src/lib/messaging/merge.ts`, not silently assumed safe. A future lane that wires a
status table for one of these kinds should extend `eitherHasPaidOrConfirmedRecord`.

D-MSG-9 (S7) · 2026-09-17 · S7 · Thread link expiry (owner decision 6) is computed once at mint time and baked into the token payload as an absolute `exp` (epoch ms); `verifyThreadToken` compares `now` against `payload.exp` only — it never re-queries the DB, staying a pure/DB-free check on every guest request. `resolveThreadTokenExpiry` (web/src/lib/messaging/thread-token.ts) takes 30 days after the LATEST live `conversation_records` date for the inquiry: `orders.created_at` for kind `order`; `admissions.starts_at` for `appointment` / `reservation` / `tickets` / `class_enrolment` (admissions is the one booking-holder table across Sessions & Classes, Reservations and Events/Ticketing — confirmed via web/src/lib/reservations/store.ts's `seatWalkIn`, which inserts a reservation directly as an admissions row carrying `starts_at`). `project` / `offer` have no date column anywhere yet and are skipped (not an error) — a record kind with no date semantics simply doesn't extend the window. D-MSG-11 (S2) · 2026-09-17 · `conversation_records` is now WRITTEN by the POS writers, through one bridge: `messaging_sync_record_state(p_tenant, p_record_kind, p_record_id)` (supabase/migrations/20261231255000_conversation_record_state.sql, SECURITY DEFINER, service_role only) called from `syncConversationRecord` (web/src/lib/messaging/record-sync.ts) AFTER each writer's own success, never before and never blocking its result. Record ids by kind: `order` = orders.id; `appointment` = agency_bookings.id; `reservation` / `tickets` / `class_enrolment` = admissions.id (reserve.ts inserts one admission per party; mint-on-paid one per seat; a session with `event_id` is `tickets`, without is `class_enrolment`). `project` and `offer` have no state table and the RPC refuses them as `invalid` (seam: whoever gives them a status table extends the CASE). Inquiries a record attaches to: orders.inquiry_id ∪ payment_links.inquiry_id (same order) ∪ agency_bookings.source_inquiry_id (booking on that order, or the booking itself); an admission reaches them through order_lines.order_id. The RPC only READS orders / order_lines / payment_links / booking_transactions / preparation_tickets / agency_bookings / booking_fulfillment / admissions / sessions (Principle 0). D-MSG-12 (S2) · 2026-09-17 · RACE NOTE. Two syncs of one record (a webhook retry racing the kitchen, or two writers on one order) must converge: the RPC derives from the source row at call time and upserts `ON CONFLICT (tenant_id, inquiry_id, record_kind, record_id) WHERE unlinked_at IS NULL` (the existing partial unique index `conversation_records_one_live`; the predicate is in the conflict target so inference works — cf. the "partial unique index broke ON CONFLICT at plan time" incident), updating only when a state actually differs (version bumps only on change; proven on the isolated branch: second call left version 1). Rows staff linked by hand to another inquiry follow the record too; a row staff UNLINKED on purpose (unlinked_at set, no live twin) is never re-linked. Cross-tenant inquiries are skipped. `syncConversationRecord` never throws, logs via logServerError, and returns `unavailable` silently when the caller's client has no `rpc` (several POS writers type their client `{ from; rpc? }` and their tests inject `from`-only fakes).

D-MSG-13 (S2) · 2026-09-17 · State vocabularies (CHECK-constrained): payment none|requested|opened|paid|failed|expired|refunded|partially_refunded|unknown; fulfilment none|hold|confirmed|preparing|ready|fulfilled|seated|checked_in|cancelled. `hold` was added to the brief's list because `deriveTasks` (S4) already reads `fulfilmentState === "hold"` for the "a hold is expiring" task; it now fires for `orders.status = pending_payment`. Mapping choices worth knowing: an open payment_link on a draft/quoted order = `requested`; pending_payment = `opened`; paid/fulfilled with order_lines.refunded_cents covering the lines = `refunded` (orders.status never becomes refunded from TS — refundOrderLines only touches lines and admissions); kitchen `queued/acknowledged/ready/handed_off_at` = confirmed/preparing/ready/fulfilled; agency_bookings `in_progress` = checked_in, `tentative/draft` = hold; booking_fulfillment `shipped|ready_for_pickup` = ready, `delivered|picked_up|downloaded|completed` = fulfilled, `returned` = cancelled; admissions `no_show_at` = cancelled (over, money kept), `seated_at` = seated, `admitted_count > 0` = checked_in. record_date: preparation_tickets.promised_at else orders.created_at; agency_bookings.starts_at else event_date; admissions.starts_at else sessions.starts_at else the order's date.

D-MSG-14 (S2) · 2026-09-17 · SEAM, not wired: `deriveAutoResolve(records, now)` (web/src/lib/messaging/lifecycle.ts, pure, 8 tests) is owner decision 1 + 14 as a function: no records → never; any record open or with unknown (null) state → open; money owed (requested|opened|failed|expired on a non-cancelled record) → open; otherwise resolve once now ≥ max(closedAt + grace) with grace 2 days (order/appointment/reservation/class_enrolment) and 7 days (tickets/project); time-anchored kinds count as closed once record_date has passed even if nobody pressed "fulfil". It returns `readyAt` so a cron can schedule the flip. NOT in this lane: the cron itself (reads live chips per open inquiry, calls `messaging_set_conversation_state` → resolved, writes the history line), the 30-day rule for conversations with no record, and the per-business grace override. The sync also does not touch `inquiries.updated_at`, so a state change alone does not reorder the inbox — the cron/UI lane decides whether it should.

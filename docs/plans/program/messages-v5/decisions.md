D-MSG-2 · 2026-09-17 · One thread-type rule. `inquiry_messages.thread_type` "private" is the CLIENT thread (staff + client/guest); "group" is the TALENT thread (staff + invited talent). Every staff-authored POS message, replies, cards and internal notes alike, is written to "private" (`threadTypeForStaffMessage` in `web/src/lib/messaging/thread-rule.ts`); the engine never writes "group". Internal notes are `message_kind = 'internal_note'` on "private" so staff see one conversation, and EVERY client-facing reader (workspace client page, `/api/client/messages`, guest dock + `/c/[inquiryId]`, `/c/t/[token]`, and the talent inbox reader) excludes that kind. Staff readers (POS `loadMessagingThread`, classic `loadInquiryMessages`) read everything and each POS ThreadMessage now carries `thread`. Evidence for the rule: before S1 the engine wrote replies to "group", which no client surface reads (a POS reply never reached the client), and wrote notes to "private", which `loadInquiryMessages` and the guest reader served unfiltered (a note reached the client). The DB trigger `messaging_touch_inquiry_from_message` already returns early on `internal_note`, so a note never flips conversation state. Enforced by `web/src/lib/messaging/client-readers.static.test.ts`.

D-MSG-9 (S7) · 2026-09-17 · S7 · Thread link expiry (owner decision 6) is computed once at mint time and baked into the token payload as an absolute `exp` (epoch ms); `verifyThreadToken` compares `now` against `payload.exp` only — it never re-queries the DB, staying a pure/DB-free check on every guest request. `resolveThreadTokenExpiry` (web/src/lib/messaging/thread-token.ts) takes 30 days after the LATEST live `conversation_records` date for the inquiry: `orders.created_at` for kind `order`; `admissions.starts_at` for `appointment` / `reservation` / `tickets` / `class_enrolment` (admissions is the one booking-holder table across Sessions & Classes, Reservations and Events/Ticketing — confirmed via web/src/lib/reservations/store.ts's `seatWalkIn`, which inserts a reservation directly as an admissions row carrying `starts_at`). `project` / `offer` have no date column anywhere yet and are skipped (not an error) — a record kind with no date semantics simply doesn't extend the window. D-MSG-40 (S6) · 2026-09-17 · S6 · Two premises in the S6 brief didn't hold and this lane worked around both rather than forcing them. (1) `cancel_booking_set` (supabase/migrations/20261231218000_cancel_booking_set.sql) cancels `agency_bookings` — the coordination-hub's own booking table — and its own header comment says "Money is not moved here": it carries NO cancellation-fee or refund-amount logic at all. No `RecordKind` a Messages v5 thread carries (`order`/`appointment`/`reservation`/`class_enrolment`/`tickets`/`project`/`offer`) resolves to an `agency_bookings` row — every schedulable kind resolves through `admissions` (D-MSG-9's `RECORD_KINDS_ON_ADMISSIONS`), and `order` resolves straight to `orders`/`order_lines`. So `messagingCancelRecord` cancels through the writer `orders`/`order_lines`/`admissions` already have — `refundOrderLines` (lib/orders/refund-execute-lines.ts), which voids the admission and releases its capacity allocation atomically — never through `cancel_booking_set`. (2) There is no `messages.request_payment`-style permission key anywhere in the repo to mirror (grepped `lib/pos`, every migration, and the capability registry `src/lib/access/capabilities.ts` for `messages.*` — zero hits), and `staff_permissions (user_id, permission)` — the one generic table shaped for this — has never been seeded or gated on anywhere (zero INSERTs in any migration; the one reader, `admin-dashboard-data.ts`, is display-only). `web/src/lib/messaging/money-permissions.ts` defines the six keys (`messages.discount`, `messages.refund`, `messages.cancel`, `messages.close_lost`, `messages.notes.read`, plus the existing `messages.request_payment` gap is left unaddressed — no caller exists to gate) fresh, OPEN BY DEFAULT PER TENANT PER KEY: if no active staff member of a tenant holds ANY row for a key, every staff member passes (today's ungated behaviour, unchanged); the moment any one of them is granted the key, that tenant has opted in and only holders (+ `super_admin`) pass. This was chosen over `src/lib/access/capabilities.ts` (the real, CI-validated, plan/role capability registry) deliberately: that registry is billing/plan-tier-gated, cross-cutting, and touching it risks colliding with whichever other wave owns `roles.ts`/`plan-capabilities.ts` — a follow-up integration lane should decide whether these six keys graduate into that registry.

D-MSG-42 (S6) · 2026-09-17 · S6 · SEAM: a `refund: {mode: "partial"|"keep"}` cancel releases capacity (`release_capacity`, the same RPC `cancel_booking_set` calls for the same purpose) but does NOT flip the admission's own `status` column to `void`/`refunded` — only `refundOrderLines`'s internal call to `refund_admission` does that atomically, and that RPC always refunds a line's FULL remaining amount (there is no "void the ticket but refund only part of its value" writer anywhere in the codebase; building one is a new writer, which Principle 0 rules out for this lane). So a `mode: "full"` cancel is airtight (money + line state + ticket void + capacity release, all atomic); a `mode: "partial"` or `mode: "keep"` cancel is airtight on money and capacity but leaves `admissions.status = 'valid'` — a door/scanner surface reading that column directly would still admit a ticket whose seat has already been freed for resale. Filed for a follow-up lane to either extend `refund_admission` to accept a partial amount, or add a standalone "void without refunding" RPC.

D-MSG-43 (S6) · 2026-09-17 · S6 · `messagingRecordOutsidePayment`'s `recordId` carries no kind (per the brief's own signature), so the workspace-booking path (`markInquiryPaidInCash`, keyed on `inquiryId` alone — it takes no record id at all) and the POS order-collection path (`recordVerifiedCollection`, keyed on `orderId`) are told apart by asking `orders` for `recordId` first. A caller-supplied `recordId` that names neither an order nor (implicitly, by omission) this inquiry's own coordination booking is silently ignored on the workspace path rather than checked, because `markInquiryPaidInCash` offers nothing to check it against. Also on this action: the three input methods (`cash`/`transfer`/`terminal_offline`) don't line up 1:1 with either rail's own method vocabulary — `recordVerifiedCollection.paidVia` is only `"cash"|"card"` (a counter tender vs. a provider session; `terminal_offline` maps to `"card"`, `cash`/`transfer` both map to `"cash"`) and `markInquiryPaidInCash`'s `PaymentMethod` is `cash|wire|venue_paid|crypto|other` (`transfer`→`wire`, `terminal_offline`→`other`, `cash`→`cash`). Both mappings are documented inline at the call sites.

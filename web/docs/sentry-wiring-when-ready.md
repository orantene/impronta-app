# Wiring Sentry when you're ready

This is the **2-step recipe** to turn on Sentry error monitoring for the
Tulala / Impronta production app. It doesn't require any code change from
us first — the SDK install is the only blocker, and you trigger it.

## What Sentry actually does (plain English)

Sentry is a "black box recorder" for your web app. Every time a real user
hits an error you didn't anticipate — a server-side exception, a broken
React component, a failed Supabase call, a Stripe webhook that crashed —
Sentry captures it, including:

- the exact error message + stack trace,
- which user was logged in (or anonymous),
- which page they were on, what they clicked just before,
- the browser / OS / region.

You see all of that in a dashboard. Without it, you find out about
production bugs when a customer emails you angrily. With it, you find out
**five seconds after the bug happens**, and you can usually reproduce +
fix before the second customer hits it.

Free tier is 5,000 errors/month — way more than you'll need pre-launch.
Sign up at https://sentry.io. Pick "Next.js" as your platform when asked.

## The 2-step recipe

### 1. Sign up + grab the DSN (5 minutes, you do this)

1. Go to https://sentry.io/signup/
2. Choose "Next.js" as your platform
3. Create a project named `tulala-web` (or whatever you want)
4. Sentry shows you a long URL that looks like:
   ```
   https://abc123def456@o1234567.ingest.sentry.io/9876543
   ```
   That's your **DSN**. Copy it.

### 2. Set the env var on Vercel (1 minute, you do this)

In Terminal:

```bash
vercel env add NEXT_PUBLIC_SENTRY_DSN production
# paste the DSN when prompted
# answer yes to sensitive

vercel env add NEXT_PUBLIC_SENTRY_DSN preview
# paste the same DSN
# answer yes to sensitive

# Trigger a rebuild so the new env vars get into the bundle:
vercel --prod --scope oran-tenes-projects
```

### 3. (We do this next) Wire the Sentry SDK

When you tell me "DSN is set," I:
- Install `@sentry/nextjs` (one npm dep, ~3MB)
- Add `sentry.client.config.ts`, `sentry.server.config.ts`,
  `sentry.edge.config.ts` (auto-generated by `npx @sentry/wizard@latest`)
- Wrap `next.config.mjs` with `withSentryConfig`
- Smoke-test by throwing a deliberate error from `/api/_dev/sentry-test`
- Confirm the error lands in your Sentry dashboard

Total time when you give me the DSN: ~30 minutes, single PR, no friction.

## Why not pre-install the SDK now

Three reasons:

1. **Cost surface**: `@sentry/nextjs` pulls in ~3MB and 30+ transitive
   deps. Installing it without a DSN is dead weight until you sign up.
2. **Alternatives exist**: Datadog, Honeybadger, BugSnag, Rollbar,
   LogRocket all do this. You might pick a different one later. Locking
   to Sentry-the-SDK before locking to Sentry-the-account is premature.
3. **Auto-activation isn't free**: Even with the SDK installed, you
   need `NEXT_PUBLIC_SENTRY_DSN` set to capture anything. The env-var
   gate is the real on/off switch — it's the same step either way.

## How to verify it's working (post-install)

After step 3, you'll be able to do this:

1. Visit `https://app.tulala.digital/api/_dev/sentry-test`
2. The route deliberately throws an exception
3. Within ~10 seconds, an error appears in your Sentry dashboard at
   https://sentry.io/organizations/<your-org>/issues/

That's your "Sentry is live" smoke test.

## What to monitor first

Once errors are flowing in, the three queues to watch:

1. **Stripe webhook errors** — these silently break booking confirmation
2. **Supabase RLS errors** — `42501` means a user hit a forbidden read
3. **`talent-self-services.ts` errors** — the new server actions from
   the Phase 1 launch lane have the most surface area

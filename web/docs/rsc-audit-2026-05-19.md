# RSC Audit — Phase F1 (2026-05-19)

Read-only static-analysis classification of every `"use client"` file
in `web/src/`. Inputs the remediation roadmap's Frontend Architecture
dimension (38 → 70). This audit is the **measurement step**; F2 and F3
do the actual migration.

## Method

`web/scripts/rsc-audit.py` scans every file in `web/src/` whose first
non-comment token is `"use client"` (allowing a leading file-header
comment block — eight files in `reservation-thread/*` and `admin/shell/
internal/messages.tsx` follow that convention). For each file it
collects six signal families:

| Family            | What we count |
|-------------------|----------------|
| **react-hooks**   | Named imports from `react` matching client-only hooks (`useState`, `useEffect`, `useReducer`, `useRef`, `useContext`, `useLayoutEffect`, `useTransition`, `useDeferredValue`, `useImperativeHandle`, `useSyncExternalStore`, `useActionState`). `useMemo` / `useCallback` / `useId` are server-safe and excluded. |
| **react-primitives** | `forwardRef`, `lazy`, `createContext` — these are not hooks but they ARE client-only because the wrapped component is ref-aware / lazy-mounted / paired with a client `<Provider>`. |
| **nav-hooks**     | `useRouter`, `usePathname`, `useSearchParams`, `useParams`, `useSelectedLayoutSegment(s)` from `next/navigation`. |
| **dom-hooks**     | `useFormState`, `useFormStatus` from `react-dom`. |
| **next-other**    | `useReportWebVitals` from `next/web-vitals`. |
| **custom-hooks**  | Any `useFoo(…)` callsite that isn't one of the above. Hook-shape calls always run on the client. |
| **client-libs**   | Imports of `framer-motion`, `react-hook-form`, `recharts`, `sonner`, `@dnd-kit/*`, `react-pdf`, `swiper`, `zustand`, `jotai`, `react-dnd`, `@react-google-maps/api`. These libraries have client-only runtime requirements. |
| **events**        | JSX attributes matching `on[A-Z][a-zA-Z]+=`, after string-literal and comment stripping so doc-comment examples don't inflate the count. |
| **browser**       | References to `window`, `document`, `navigator`, `localStorage`, `sessionStorage`, `IntersectionObserver`, `ResizeObserver`, `MutationObserver`, `FileReader`, `matchMedia`, `request/cancelAnimationFrame`, used as a member access or call (e.g. `window.matchMedia(`). |
| **jsx-nodes**     | Total JSX opening tags. Used for the B vs A density check. |

The new admin Tailwind utility classes (`bg-admin-*`, `text-admin-*`)
land in className strings only and have no client semantics — they are
ignored by every detector. Same for the 56 admin design-token CSS vars
added in Y4 (decorative).

### Classification rules (in priority order)

1. **C — hook file**: `.ts` file under `web/src/hooks/` (or filename
   starting with `use-`) that contains no JSX. Hook files are client-
   only by definition — they define the client behaviour that other
   components consume.
2. **A — no client signals at all**: the file has zero hooks, zero
   primitives, zero event handlers, zero browser-global references,
   and no client-only library imports. Removing `"use client"` is
   safe; the file becomes a Server Component (or, more precisely, a
   "shared" component the React compiler can render in either
   environment).
3. **C — client-only library** (framer-motion, recharts, react-hook-
   form, sonner, dnd-kit, …): hard requirement.
4. **C — heavy state**: ≥3 `useState` calls. Empirically these are
   genuine state machines, not extractable islands.
5. **C — `useReducer` / `useLayoutEffect`**: same reasoning — sticky
   client state.
6. **C — `useContext`** (outside admin shell): the file is plumbed
   into a client provider tree.
7. **C — `forwardRef` / `lazy` / `createContext`** (with any other
   interactivity or LOC ≥ 100): see "react primitives" above.
8. **C — edit-chrome with any interactivity**: the live-editor surfaces
   are client-by-charter (Phase F5 tightens the boundary; F1/F2/F3
   don't touch them).
9. **C — navigation hook + state/effect**: `useRouter` /
   `useSearchParams` paired with `useState` or `useEffect` is a
   route-aware interactive shell.
10. **C — huge file (LOC ≥ 1500)**: too coarse for island extraction
    in F3; leave for the editor-chrome / state-hoisting passes.
11. **B — pathname-only nav**: file uses `usePathname` for active-link
    highlighting and nothing else. The interactive piece is the
    `<Link aria-current>` strip; the rest is static markup.
12. **B — useTransition + ≤3 handlers**: thin actions over a static
    shell.
13. **B — static wrapper + ≤2 handlers, density < 0.20**: catches
    pickers, drawer rows, peek cards. Effort estimate scales with
    LOC.
14. **C — fallthrough** for anything else with interactivity.

The estimates are deliberately conservative: a wide A bucket and a
narrow B bucket means F2 (the easy class) lands cleanly and F3 (the
careful work) only takes on what the heuristic is confident about.
Unsure files go to the C bucket by design — better to under-promise
extraction than to over-promise it and stall mid-batch.

## What this audit does NOT do

- It does NOT remove any `"use client"` directive. (F2.)
- It does NOT extract any islands. (F3.)
- It does NOT classify by "this would be a good RSC migration" —
  it classifies by "the file itself has no client requirement
  visible from static analysis." A Class A file inside a Client
  parent stays in the client bundle regardless. The win materialises
  when the parent flips too — that's F2/F3/F4's cumulative effect.
- It does NOT detect dynamic-import boundaries (`next/dynamic` with
  `ssr: false`). Counted ad-hoc: 0 occurrences in `use-client`
  files (most `next/dynamic` calls live in server-component parents).
- It does NOT measure runtime bundle impact. The score win is
  *clarity + roadmap*; bundle-size reduction is downstream of F2/F3
  shipping.

## Honest imperfections

1. **JSX-node count on `.ts` files**: occasionally reports `jsx-nodes:1`
   for TypeScript-generic syntax that resembles `<TagName`. Doesn't
   affect classification (no JSX-bearing logic survives the rules
   above) but it's noise in the CSV's `interactivity_signals` column.
2. **Custom-hook detection is broad**: any `useFoo(…)` callsite triggers
   the custom-hooks bucket. Some of these (e.g. user-defined utility
   functions like `useUserSettings`) are genuine client hooks; some
   (e.g. RSC-safe helpers misnamed `use*`) might be false positives.
   Currently the classifier counts all of them as client signals
   because the false-positive rate is < 5% in spot checks and Class C
   is the safer default.
3. **Hook files under `web/src/lib/ui/*-hook.ts` are NOT detected** as
   hook files by the filename heuristic — they're classified by their
   internal signals. In practice this works (they all have `useState`
   or `useEffect`) but the bucketing isn't pristine.
4. **No coupling analysis**: the audit doesn't know whether a Class A
   file is currently imported by a server component (immediate win) or
   only by client components (latent win — flips when the parent
   migrates). F2 will need to do this analysis when batching.
5. **The "B" bucket is conservative.** F4 (state-management hoisting)
   will surface a new wave of B candidates currently bucketed as C
   because of multiple `useState`. Re-run `python3 web/scripts/rsc-
   audit.py` after F4 lands to refresh the CSV.
